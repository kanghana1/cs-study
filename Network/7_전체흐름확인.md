# 주소창에 google.com을 친다면?

### **요약**

```
① URL 입력 & 파싱
② DNS 조회 (도메인 → IP)
③ TCP 연결 (3-way handshake)
④ TLS 핸드셰이크 (HTTPS인 경우)
⑤ HTTP 요청 전송
⑥ 서버 처리 & HTTP 응답
⑦ 브라우저 렌더링
⑧ 연결 종료 (4-way handshake)
```

<br>

## **1. URL 입력 & 파싱**

브라우저가 입력된 URL을 분석한다.

```
https://google.com/search?q=cs
└─┬─┘  └────┬────┘└──┬──┘
프로토콜    도메인    경로/쿼리
```

- 프로토콜(https), 도메인(google.com), 경로 등을 분리한다.
- 브라우저는 먼저 **캐시를 확인**한다. 정보가 이미 있으면 일부 단계를 건너뛴다.
- <br>

## **2. DNS 조회 (도메인 → IP)**

도메인 이름으로는 통신할 수 없으니 **IP 주소로 변환**한다.

```
브라우저 캐시 → OS 캐시 → Local DNS(Resolver) 확인
        ↓ 없으면
Resolver → Root → TLD → Authoritative 순으로 조회
        ↓
google.com → 142.250.207.46 획득
```

- 캐시에 있으면 바로 사용, 없으면 계층적으로 조회한다.
- TTL 동안 결과가 캐시된다.
- <br>

## **3. TCP 연결 (3-way handshake)**

IP를 알았으니 그 서버와 **연결을 맺는다.**

```
클라이언트 → 서버 : SYN
서버 → 클라이언트 : SYN + ACK
클라이언트 → 서버 : ACK
        ↓
연결 성립 (양방향 통신 확인 완료)
```

- 소켓의 `connect()`가 내부적으로 이 핸드셰이크를 수행한다.
- 실제로는 데이터가 라우터를 거쳐 가며(라우팅), 각 구간마다 **ARP로 다음 기기의 MAC을 찾아** 프레임을 전달한다.

<br>

## **4. TLS 핸드셰이크 (HTTPS인 경우)**

암호화 통신을 위한 핸드셰이크를 수행한다.

```
Client Hello → Server Hello + 인증서
        ↓
인증서 검증 (CA 공개키로) → 서버 신원 확인
        ↓
Pre-Master Secret 교환 (서버 공개키로 암호화)
        ↓
양쪽이 세션키(대칭키) 생성
        ↓
이후 암호화 통신 준비 완료
```

- 이 단계를 거쳐야 이후 HTTP 데이터가 암호화되어 안전하게 오간다.

<br>

## **5. HTTP 요청 전송**

실제 요청을 보낸다.

```
GET /search?q=cs HTTP/1.1
Host: google.com
User-Agent: Chrome
Cookie: sessionId=abc123    ← 쿠키가 있으면 자동 첨부
```

- 메서드(GET), 경로, 헤더를 담아 보낸다.
- 로그인 상태라면 쿠키(세션 ID나 토큰)가 함께 실린다.
- HTTPS라 요청 전체가 세션키로 암호화되어 전송된다.

<br>

## **6. 서버 처리 & HTTP 응답**

서버가 요청을 처리하고 응답한다.

```
HTTP/1.1 200 OK
Content-Type: text/html
Set-Cookie: ...           ← 필요시 쿠키 설정

<html>...</html>          ← 실제 콘텐츠
```

- 서버는 요청을 처리(DB 조회 등)한 뒤, 상태 코드와 콘텐츠를 응답한다.
- 이 응답도 암호화되어 온다.

<br>

## **7. 브라우저 렌더링**

받은 HTML을 화면에 그린다.

```
HTML 파싱 → DOM 트리 생성
CSS 파싱  → 스타일 적용
        ↓
HTML 안의 추가 리소스(CSS, JS, 이미지) 발견
        ↓
각 리소스마다 다시 요청 (②~⑥ 반복)
        ↓
최종 화면 완성
```

- HTML 하나로 끝이 아니라, 내부의 이미지·CSS·JS를 **각각 또 요청**한다.
- 그래서 앞의 과정이 여러 번 반복된다.
- **HTTP 버전과 연결되는 지점:** HTTP/1.1은 순차 처리로 느렸고(HOL Blocking), HTTP/2는 멀티플렉싱으로 병렬 처리했다. 성능 차이가 바로 이 렌더링 단계의 리소스 요청에서 드러난다.
- <br>

## **8. 연결 종료 (4-way handshake)**

통신이 끝나면 연결을 정리한다.

```
FIN → ACK → FIN → ACK
        ↓
연결 종료
```

- 단, Keep-Alive로 연결을 유지했다가 재사용하기도 한다. 매번 연결을 새로 맺는 비용이 크기 때문이다.

<br>

## 계층 구조로 보기

이 모든 과정은 계층 구조 위에서 일어난다.

| 계층            | 이 흐름에서 하는 일                   |
| --------------- | ------------------------------------- |
| 응용 계층       | DNS, TLS, HTTP 요청/응답              |
| 전송 계층       | TCP 연결(3-way), 포트로 프로세스 지정 |
| 네트워크 계층   | IP로 목적지 찾기, 라우팅              |
| 데이터링크 계층 | ARP로 MAC 찾기, 프레임 전달           |
| 물리 계층       | 실제 신호 전송                        |

주소 변환의 흐름:

```
google.com  ─(DNS)→  IP 주소  ─(ARP)→  MAC 주소  →  실제 전송
```
