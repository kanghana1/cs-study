# 3. HTTP 심화

## **HTTP 메서드**

HTTP 메서드는 서버에 무엇인가를 요청할 때 사용하고, 용도에 따라 여러가지가 있다.

### **1. GET**

GET 메서드는 **서버에 데이터를 요청**할 때 사용한다. 요청하는 데이터가 HTTP Request Message의 Header 부분에 url 이 담겨서 전송되기 때문에 때문에 url 상에 ? 뒤에 데이터가 붙어 request 를 보내게 된다.

이러한 방식은 url 이라는 공간에 담겨가기 때문에 전송할 수 있는 데이터의 크기가 제한적이다.

또, 조회를 하는 메서드이므로 **서버의 데이터를 바꾸지 않**는다. **(Safe)**

### **2. POST**

POST 메서드는 **서버에 데이터를 생성**할 때 사용한다. 요청하는 데이터가 HTTP Request Message의 Body 부분에 담겨서 전송되기 때문에 url 상에 데이터가 붙지 않고, 전송할 수 있는 데이터의 크기가 제한적이지 않다.

이러한 방식은 url 이라는 공간에 담겨가지 않기 때문에 전송할 수 있는 데이터의 크기가 제한적이지 않다.

또, 서버의 데이터를 생성하는 메서드이므로 **서버의 데이터를 바꾼다.** **(Unsafe)**

### **3. PUT**

PUT 메서드는 **데이터를 전체 수정**할 때 사용한다. 리소스 전체를 통째로 바꾼다는 특징이 있다.

### **4. PATCH**

PATCH 메서드도 데이터를 수정할 때 사용하지만, **부분 수정**을 한다는 점에서 PUT과 다르다.

### **5. DELETE**

DELETE 메서드는 서버에서 **데이터를 삭제** 요청할 때 사용한다.

 <br>

위 메서드들을 분류하는 두 가지 중요한 특성이 있다.

- **안전성 (Safe)**
  - **서버의 데이터를 바꾸지 않는 성질**
  - GET이 대표적 (조회만 하므로 여러번 호출해도 서버가 변하지 않음)
- **멱등성 (Idempotent)**
  - 여러 번 호출해도 결과가 같은 성질
  - GET, PUT, DELETE는 멱등하지만, PATCH와 POST는 멱등하지 않음
    - 엄밀히 말하면 PATCH는 멱등할수도, 아닐수도 있음 (로직에 따라 다름)

<br>

## **HTTP 버전**

HTTP 메서드는 서버에 무엇인가를 요청할 때 사용하고, 용도에 따라 여러가지가 있다.

### **HTTP/1.0**

HTTP/1.0은 1996년에 RFC 1945로 정의되었으며, HTTP의 첫 번째 버전이다. HTTP/1.0은 요청과 응답을 위해 TCP 연결을 사용하며, 요청마다 새로운 연결을 생성한다.

요청 하나를 보낼 때마다 연결을 맺고, 응답을 받으면 끊는 과정을 반복하는데 웹페이지 하나에는 수십개의 요청이 필요하기 떄문에 **비용이 많이 든다.**

### **HTTP/1.1**

HTTP/1.1은 1999년에 RFC 2616으로 정의되었으며, HTTP/1.0의 단점을 개선한 버전이다.

HTTP/1.1은 요청과 응답을 위해 **TCP 연결**을 사용하며, 요청마다 새로운 연결을 생성하지 않고, **Keep-Alive 기능**을 통해 연결을 유지해 재사용함으로써 연결 비용을 크게 줄였다.

다만, 연결은 재사용하는데, 요청을 보낸 순서대로 응답해야해서 **앞 요청의 응답이 늦으면 뒷 요청들이 막힌다**는 문제점이 있었다. (이를 **HOL Blocking**(Head-of-Line Blocking, 머리 막힘) 이라고 한다)

### **HTTP/2 - 멀티플렉싱**

HTTP/2는 2015년에 RFC 7540으로 정의되었으며, HTTP/1.1의 을 개선한 버전이다.

**멀티플렉싱**을 이용하여 하나의 연결에서 여러 요청, 응답을 순서에 상관없이 주고받는다.

> 🔗 **멀티플렉싱 (Multiplexing)**
>
> 하나의 물리적 또는 논리적 통로(채널/연결)를 통해 여러 개의 신호나 데이터를 동시에 주고받는 기술을 의미한다.
>
> 데이터를 잘게 쪼갠 프레임으로 나누고, 요청/응답마다 스트림ID를 붙여 순서가 뒤섞여있어도 조립할 수 있도록 한다.

HTTP/2는 애플리케이션에서는 병렬이 되지만, **TCP 계층에서는 여전히 HOL Blocking 문제**가 남아있게 된다.

### **HTTP/3 - QUIC**

HTTP/3는 2020년에 RFC 9000으로 정의되었으며, HTTP/2의 단점을 개선한 버전이다.

TCP는 순서 보장을 해준다는 특징이 있는데 이 특징으로 인해 HOL Blocking이라는 문제가 있었다.

그렇기 떄문에 TCP를 사용하지 않고, **UDP 기반의 QUIC**라는 프로토콜을 사용해 이 문제를 해결했다.

> 🔗 **QUIC 프로토콜**
>
> QUIC는 HTTP와 UDP 사이에서 신뢰성과 순서를 보장하는 프로토콜이다. TCP는 전체를 한 줄로 세워 순서를 보장했으나, QUIC는 스트림별로 순서를 보장한다.

## **로그인 유지하기 (쿠키/세션/토큰)**

위에서 살펴봤듯이 HTTP는 stateless 하다. 즉, 이전 요청을 기억하지 못하기 때문에, 해당 요청을 보낸 사람이 누구인지 기억할 수 없다.

그런데 서비스에선 로그인을 유지시켜야 하기 때문에, 세션 및 토큰을 사용한다.

### **쿠키 (Cookie)**

쿠키는 서버가 클라이언트에게 보내는 작은 데이터이다. 쿠키는 브라우저에 저장되며, 브라우저가 서버에 요청을 보낼 때마다 쿠키를 함께 전송한다.

**주요 속성**

- **Expires / Max-Age**
  - 쿠키의 유효기간
  - 없으면 브라우저를 닫을 때 사라짐(세션 쿠키)
- **HttpOnly**
  - 자바스크립트에서 쿠키에 접근하지 못하게 막음
  - XSS 공격으로 쿠키를 탈취당하는 걸 방지
- **Secure**
  - HTTPS 연결에서만 쿠키를 전송하게 강제함
  - 평문으로 새어나가는 걸 막아줌
- **SameSite**
  - 다른 사이트에서 요청할 때 쿠키를 보낼지 제어
  - CSRF 공격 방어에 쓰임

### **세션 (Session)**

세션은 **서버가 클라이언트의 상태를 저장**하는 방식이다. 세션은 서버에 저장되며, 클라이언트는 세션 ID를 쿠키에 담아 서버에 전송한다.

```
1. 로그인 성공
        ↓
2. 서버가 세션 저장소에 사용자 정보 저장
   { "abc123" : { userId: 7, name: "하나" } }
        ↓
3. 클라이언트에 세션 ID만 전달 (쿠키에 담아서)
   Set-Cookie: sessionId=abc123
        ↓
4. 이후 요청마다 쿠키로 세션 ID가 자동 전송
        ↓
5. 서버가 세션 ID로 저장소를 조회해서 "아 7번 사용자구나" 확인
```

**장점**

- 서버에서 상태를 관리하기 때문에, 클라이언트가 조작할 수 없음
- 보안에 유리함. 세션을 탈취당해도 정보가 노출되진 않음
- 강제 로그아웃이 필요한 경우 세션을 지우는 방식으로 즉시 무효화 가능

**단점**

- 서버에서 상태를 관리하기 때문에, 서버에 부하가 걸림
- 서버 확장 (Scale out)이 까다로움.
  - 1번 서버에 로그인했는데 다음 요청이 2번 서버로 가면, 2번 서버엔 그 세션이 없어 문제가 됨
  - 이를 해결하기 위해 보통 Redis 같은 **공용 세션 저장소를 사용**함

### **토큰 / JWT (Json Web Token)**

토큰은 **클라이언트가 상태를 저장**하는 방식이다. 토큰은 클라이언트에 저장되며, 클라이언트는 토큰을 Authorization Header에 담아 서버에 전송한다.

```
1. 로그인 성공
        ↓
2. 서버가 사용자 정보를 담은 토큰을 생성하고 서명함
   (저장은 안 함!)
        ↓
3. 클라이언트에 토큰 전달
        ↓
4. 이후 요청마다 토큰을 헤더에 담아 전송
   Authorization: Bearer eyJhbGci...
        ↓
5. 서버는 토큰의 서명만 검증 → 유효하면 신뢰
```

서버가 저장소를 조회하지 않고 토큰 자체를 검증한다.

#### **✔️ JWT 구조**

JWT는 세 부분으로 나뉘어져 있다.

```
eyJhbGciOi... . eyJ1c2VySWQi... . SflKxwRJSM...
   Header          Payload         Signature
```

- **Header** 는 어떤 알고리즘으로 서명했는지 담음
- **Payload** 는 실제 담을 정보 (사용자 ID, 만료 시간 등)
- **Signature** 는 서버만 아는 비밀키로 만든 서명으로 이를 통해 위조를 감지함

여기서 **Payload는 암호화가 아니라 인코딩**이기 때문에 누구나 디코딩해서 내용을 볼 수 있다. 따라서 JWT에는 민감정보가 들어가면 안된다.

**장점**

- 서버에서 상태를 관리하지 않기 때문에, 서버에 부하가 적음
  - HTTP의 stateless에 더 부합
- 서버 확장에 용이

**단점**

- 토큰 자체에 정보가 담겨있기 때문에, 탈취당하면 정보가 노출될 수 있음
- 서버가 즉시 무효화하기 어려움 (만료시간까지 계속 유효)

<br>

## **HTTPS / TLS**

HTTPS를 이해하려면 HTTP가 어떤식으로 데이터를 주고 받는지 알아야 한다.

### **HTTP의 문제점**

HTTP의 치명적인 문제는 **데이터를 평문으로 주고 받는다는 것**이다. 암호화가 전혀 되지 않아 데이터가 그대로 노출된다.

그래서 중간에서 통신을 엿보거나 조작하는 **중간자공격 (Man in the Middle, MITM)** 에 취약하다.

<br>

### **HTTPS**

HTTPS는 HTTP에 **TLS(Transport Layer Security)라는 암호화 계층**을 적용한 것이다. 

즉 HTTP의 데이터를 **TLS로 암호화**해서 전송하기 때문에, 중간에서 누군가가 데이터를 가로채더라도 내용을 알 수 없게 된다.

이때 TLS란, 실제 암호화를 담당하는 프로토콜로, 이전에는 SSL이 있었고 SSL을 개선해나간 게, 지금의 TLS라고 한다.

**HTTPS 특징**

HTTPS는 다음 세 가지를 보장해준다.

- 기밀성 (Confidentiality) : 중간에서 엿볼 수 없음
- 무결성 (Integrity) : 데이터가 중간에 조작되면 감지함
- 인증 (Authentication) : 신뢰할 수 있는 서버인지 확인함

<br>

> **🔗 암호화 - 대칭키와 비대칭키**
>
> **대칭키**
> 
> 암호화와 복호화에 같은 키를 쓰는 방식
>
> - 장점 
>   - **속도가 빠름** (연산이 단순)
> - 단점
>   - 키를 안전하게 전달하는게 어려움
>
> **비대칭키**
>
> 대칭키의 키 전달문제를 해결한 방식으로 키가 **공개키와 개인키**로 두 개임
>
> 한 키로 잠그면, 다른 한 키로 열 수 있음
>
> - 장점
>   - 키 전달 문제가 사라짐
>   - 공개키는 아무나 가져도 되고, 개인키는 서버에서만 갖고있으면 됨
> - 단점
>   - 대칭키보다 연산이 복잡해 **속도가 느림**
>   - 다 비대칭키로 암호화하면 성능문제
>
> 때문에 TLS는 두 방법을 적절히 조합해 사용한다.


### **인증서와 CA**

위에서 암호화 키를 봤듯이, 어쩃든 키를 받아야 한다. 그런데 내가 받은 키가 해당 서버의 공유키인지 어떻게 신뢰할 수 있을까?

이때, **인증서**를 통해 신뢰성을 검증한다. 인증서는 서버의 공개키와 서버 정보를 담고 있으며, **인증기관(CA, Certificate Authority)이 서명**한 것이다.

<br>

**CA (Certificate Authority)**

CA는 **공개키의 주인이 진짜인지 보증해주는 신뢰할 수 있는 기관**이다.

**공개키가 진짜 이 도메인의 것인지를 CA가 보증**하는 전자 문서가 바로 **인증서**이다.

**인증서 구성**
```
인증서 내용
├── 서버의 도메인 (예: google.com)
├── 서버의 공개키  -- 대상
├── 발급한 CA 정보
├── 유효기간
└── CA의 디지털 서명 🌟 
```

<br>

#### **CA가 보증하는 방법**

CA도 자기만의 개인키/공개키가 있다. CA가 인증서를 발급할 때, **인증서 내용을 CA의 개인키로 서명**한다.

비대칭키의 특성상, 우리는 이 **서명을 CA의 공개키로 검증**할 수 있다. 서명이 제대로 풀리면 CA가 서명했다는 것을 믿을 수 있게 되는 것이다.

CA의 공개키는 브라우저와 운영체제에 미리 내장되어있기 때문에 공개키는 신뢰할 수 있다!


<br>

## **TLS 핸드셰이크**
