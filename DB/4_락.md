# 4. 락 (Lock)

## **락이 필요한 이유**

여러 트랜잭션이 같은 데이터에 동시에 접근하면 문제가 생긴다. 특히 동시 수정을 하려 할 때 다음과 같은 문제가 생길 수 있다.

```
트랜잭션A: 재고 10개 읽음 → 1개 팔아서 9개로 수정하려 함
트랜잭션B: 재고 10개 읽음 → 1개 팔아서 9개로 수정하려 함
        ↓
둘 다 10을 읽고 9로 저장 → 실제론 2개 팔렸는데 재고는 9개!
(1개가 증발, 실제는 8개여야 함)
```

동시에 접근해서 한 쪽의 변경이 사라지는 상황이다. 이런 상황을 **갱신 손실 (Lost Update)** 라고 한다.

락은 이런 동시 접근 문제를 막기 위해 **데이터에 잠금을 걸어 순서를 제어**하는 장치이다.

<br>

### **MVCC와의 차이점**

앞서 배운 MVCC와 락의 차이는 무엇일까?

- MVCC : 읽기와 쓰기 충돌을 피하기 위한 장치
- 락 : 동시 수정 충돌을 피하기 위한 장치

동시에 수정하는 상황은 MVCC로 막을 수 없다. 그래서 결국은 쓰기 충돌에 락이 필요하다.

<br>

## **공유 락과 배타 락**

락에는 크게 두 종류가 있다. 읽기용과 쓰기용이라고 생각하면 된다.

### **공유 락 (Shared Lock, S Lock)**

공유 락은 **읽기 전용 잠금**이다. 공유 락이 걸린 데이터는 다른 트랜잭션이 읽을 수는 있지만, 수정은 할 수 없다.

공유 락이 걸린 상황에서 다른 트랜잭션이 읽기를 수행할 수 있기 때문에, **여러 트랜잭션이 동시에 걸 수 있다**는 특징이 있다.

> **🔗 공유락과 MVCC**
>
> 락이 필요한 이유가 쓰기와 읽기의 충돌 때문이라면, 공유락은 왜 필요할까?
>
> InnoDB에서 **일반적인 SELECT는 공유락을 걸지 않고 MVCC로 처리**한다. 즉 평범한 읽기에서는 MVCC가 있기 떄문에 공유락을 쓰지 않는다.
>
> 공유락이 필요한 때는 MVCC로 되지 않는 경우이다. 예를 들어 **확실하게 최신값을 읽어야 할 때는 MVCC를 사용할 수 없기 때문에, 공유락이 필요**해진다.

### **배타 락 (Exclusive Lock, X Lock)**

배타 락은 **쓰기 전용 잠금**이다. 배타 락이 걸린 데이터는 다른 트랜잭션이 읽거나 수정할 수 없다. 따라서 공유락과 달리 **혼자만 걸 수 있다**는 특징이 있다. (공유 락도 걸 수 없다.)

<br>

## **락의 범위**

락을 어느 단위로 거느냐도 중요한 요소이다. 범위가 다르면 성능과 안전성이 달라진다.

### **행 락 (Row Lock)**

행 락은 **특정 행에만 락을 거는 것**이다. 행 단위로 락을 걸기 때문에, 다른 트랜잭션이 다른 행에는 접근할 수 있다. 그래서 **동시성(Concurrency)이 높다**는 장점이 있다. InnoDB의 기본이다.

### **테이블 락 (Table Lock)**

테이블 락은 **테이블 전체에 락을 거는 것**이다. 테이블 단위로 락을 걸기 때문에, 다른 트랜잭션은 그 테이블에 접근할 수 없다. 그래서 **동시성이 낮다**는 단점이 있다.

<br>

보통 행 락이 유리하지만, **테이블의 대부분 행을 바꾸는 경우**에는 테이블 락이 더 효율적이다. 또 **스키마 변경이 필요한 경우**에도 테이블 락을 사용한다.

<br>

## **낙관적 락과 비관적 락**

락을 어떤 관점으로 접근하느냐에 따라 낙관적 락과 비관적 락으로 나눌 수 있다.

### **낙관적 락 (Optimistic Lock)**

낙관적 락은 **충돌이 거의 없을 것이라고 낙관적으로 보고, 충돌이 발생했을 때만 처리**하는 방식이다. 그래서 락을 걸지 않고, 트랜잭션이 끝날 때 충돌 여부를 확인한다.

중요한 특징은 **버전 칼럼**이 있다는 것이다.

```
① 데이터를 읽을 때 version도 같이 읽음 (version = 1)
② 수정할 때 "내가 읽은 version이 아직 그대로인지" 확인
   UPDATE ... WHERE id=1 AND version=1
③ version이 그대로면 → 수정 성공 + version을 2로 올림
   version이 바뀌었으면 → 그새 누가 수정한 것 → 충돌! → 실패 처리
```

락을 걸지 않기 때문에 성능 부담이 적다. 대신 충돌이 날 경우 그때 감지해 **재시도를 하거나 예외처리**를 한다.

충돌이 많아져 재시도가 늘어나면 락을 거는 것보다 안 좋기 때문에 **충돌이 드문 상황에서 적합**하다.

### **비관적 락 (Pessimistic Lock)**

비관적 락은 **충돌이 발생할 것이라고 비관적으로 보고, 아예 락을 걸어버리는 방식**이다. 그래서 트랜잭션이 끝날 때까지 다른 트랜잭션이 접근하지 못한다.

```
데이터를 읽는 순간부터 배타 락을 걸어버림
→ 다른 트랜잭션은 아예 접근 못 함 (대기)
→ 내가 끝날 때까지 독점
```

앞서 배운 공유/배타 락을 직접 거는 게 비관적 락이다. 충돌을 확실히 막을 수 있지만, 락을 오래 잡으면 다른 트랜잭션이 대기를 하기 때문에 **성능이 떨어질** 수 있다. 따라서 **충돌이 자주 일어나는 상황에 적합**하다.

<br>

## **데드락 (Deadlock)**

데드락은 **두 트랜잭션이 서로 상대방이 가진 락을 기다리면서 무한 대기 상태에 빠지는 것**을 말한다.

```
트랜잭션A: 데이터1에 락 걸고 → 데이터2의 락을 기다림
트랜잭션B: 데이터2에 락 걸고 → 데이터1의 락을 기다림
        ↓
서로 상대가 가진 걸 기다림 → 둘 다 영원히 멈춤
```

### **DB는 어떻게 처리할까**

DB는 데드락을 감지하면 한 쪽 트랜잭션을 강제로 롤백시킨다. 롤백된 트랜잭션은 보통 애플리케이션에서 재시도를 한다.

### **예방방법**

데드락을 예방하는 방법은 크게 두 가지가 있다.

1. **락을 거는 순서를 정해놓기**
   - 모든 트랜잭션이 데이터1 → 데이터2 순으로 락을 걸면, 순환 대기가 생기지 않는다.
2. **락 범위와 시간 최소화**
   - 락을 필요한 만큼만, 짧게 잡으면 충돌이 줄어든다.
