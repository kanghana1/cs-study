# 인덱스 (Index)

## **인덱스란?**

테이블에서 특정 회원을 찾기 위해서는 DB를 첫 줄부터 마지막 줄까지 전부 훑어야 한다. 이를 **풀 테이블 스캔 (Full Table Scan)** 이라고 한다. 이렇게 되면, 데이터가 많을수록 **성능이 나빠**질 수밖에 없다. 이러한 문제를 해결하기 위해 나온 것이 인덱스이다.

인덱스는 책의 **목차**처럼, 특정 데이터를 빠르게 찾을 수 있도록 도와주는 자료 구조이다. 인덱스를 사용하면, DB는 테이블의 모든 데이터를 훑지 않고도 원하는 데이터를 바로 찾을 수 있다.

<br>

## **인덱스의 원리**

인덱스가 빠른 이유는 **데이터가 정렬**되어 있기 때문이다. 이진탐색을 생각하면 된다.

```
정렬 안 됨: [5, 2, 8, 1, 9, 3, 7] → 하나씩 다 비교 (느림)
정렬 됨:    [1, 2, 3, 5, 7, 8, 9] → 범위를 절반씩 좁힘 (빠름)
```

인덱스는 특정 컬럼의 값을 미리 정렬해서 별도로 저장해둔다. 그래서 그 컬럼으로 검색할 때 정렬의 이점을 활용해 빠르게 찾는다.

### **B-Tree 구조**

**B-Tree (정확히는 B+Tree)** 는 **대부분의 DB 인덱스가 쓰는 자료구조**이다.

데이터의 삽입/삭제가 계속 일어나기 때문에 단순 배열이 아닌 트리구조로 이루어져있다.

#### **기본 형태**

```
                [ 50 ]              ← 루트 노드
               /      \
          [20 30]    [70 80]        ← 중간 노드
          /  |  \    /  |  \
        ...  ... ...              ← 리프 노드 (실제 데이터 위치)
```

특징은 다음과 같다.

- **균형 트리(Balanced)**
  - 모든 리프 노드가 같은 높이에 있다.
  - 그래서 어떤 값을 찾든 비슷한 횟수로 도달한다. (검색 성능이 일정하다)
- **탐색 과정**
  - 루트에서 시작해 값을 비교하며 아래로 내려간다.

이렇게 높이가 낮게 유지되기 때문에, 데이터가 많아도 적은 단계로 데이터를 찾을 수 있다.

<br>

#### **B+Tree의 특징**

MySQL을 포함한 실제 DB는 B-Tree를 개선한 B+Tree를 쓴다. B-Tree와의 차이는 다음과 같다.

- **실제 데이터는 리프 노드**에만 있다.
  - 중간 노드는 길을 안내하는 이정표 역할만 한다.
  - 데이터는 전부 맨 아래 리프에 모여있다.

- **리프 노드끼리 연결**되어 있다.
  - 리프 노드들이 서로 링크로 이어져 있어서, **범위 검색에 강하다.**
  - ex| "20 이상 80 이하"를 찾을 때, 20을 찾은 뒤 리프를 따라 옆으로 쭉 읽으면 된다. 다시 위에서부터 탐색할 필요가 없다.

만약 데이터를 삽입할 때 정렬된 상태에서 제각각의 값이 들어온다면 사이를 비집고 들어와야 한다. 이미 꽉 차있으면 **페이지 분할도 필요**하다.

이러한 이유로 **PK는 되도록 순차적으로 증가하는 값**을 쓰는 게 좋다! 여기서 **UUID를 PK로 쓰면 성능이슈**가 있다는 말이 나오는 것이다.

<br>

## **클러스터형 인덱스 VS 보조 인덱스**

인덱스는 크게 두 종류로 나뉜다.

```
클러스터형 인덱스 (Clustered Index)  → 데이터 자체가 정렬됨
보조 인덱스 (Secondary Index)        → 위치만 가리킴
```

이 둘의 차이가 정말 중요하다.

### **클러스터형 인덱스 (Clustered Index)**

클러스터형 인덱스는 **데이터가 인덱스 순서대로 물리적으로 정렬되어 저장**되는 방식이다.

**InnoDB에서도 기본키(PK)가 자동으로 클러스터형 인덱스**가 된다.

또 클러스터형 인덱스는 보조 인덱스 (일반 인덱스)와 다르게 **리프노드에 실제 데이터가 통째로** 들어있다. 즉, 인덱스이면서 동시에 데이터 저장소인 셈이다. 그래서 PK 검색이 아주 빠르다!

```
클러스터형 인덱스 (PK 기준)
                [ 50 ]
               /      \
         [20]          [80]
        /    \        /    \
   리프: [10, 홍길동, 30세] [20, 김철수, 25세] ...
         └── 실제 데이터 전체가 여기 있음! ──┘
```

한 가지 제약이 있다면, **데이터를 물리적으로 한 가지 순서로만 정렬할 수 있어 클러스터형 인덱스는 테이블 당 하나** 뿐이다. 따라서 PK 하나에만 적용된다.

### **보조 인덱스 (Secondary Index)**

보조 인덱스는 PK가 아닌 다른 칼럼에 만드는 인덱스이다. **테이블에 여러 개** 만들 수 있다.

데이터는 이미 PK로 물리 정렬이 되어있기 때문에, **보조 인덱스의 리프는 결국 PK 값**을 가리킨다!

```
보조 인덱스 (이름 기준)
                [ 김 ]
               /      \
         [강]          [박]
        /    \
   리프: [김철수 → PK:20] [박영희 → PK:35] ...
         └── 데이터가 아니라 PK를 가리킴 ──┘
```

#### **데이터가 아닌 PK를 가리키는 이유**

데이터의 위치가 바뀔 수 있기 때문이다. 예를 들어, INSERT를 하면 페이지 분할이 일어날 수 있는데 이때 물리적 위치가 옮겨진다. 만약 **보조 인덱스가 물리적 위치를 직접 가리키면, 데이터가 옮겨질 때마다 모든 보조 인덱스를 다 수정**해야 한다.

그런데 PK를 가리키게 하면, 데이터가 옮겨져도 PK는 바뀌지 않기 때문에 보조 인덱스를 고칠 필요가 없게 된다.

따라서 **보조 인덱스 검색은 탐색이 두 번** 일어난다.

```
"김철수" 검색 (이름은 보조 인덱스)

1차 탐색: 보조 인덱스(이름)에서 "김철수" 찾음 → PK:20 획득
        ↓
2차 탐색: 클러스터형 인덱스(PK)에서 PK:20 찾음 → 실제 데이터 획득
```

<br>

**🔗 참고**

> 하지만 이건 DB마다 다르기 때문에! 따로 공부해야한다. 이 정리는 InnoDB를 기준으로 정리했고, Oracle의 경우는 데이터 정렬 없이 물리 위치로 접근한다.

<br>

## **커버링 인덱스 (Covering Index)**

쿼리에 필요한 모든 칼럼이 인덱스 안에 다 들어있어서 **실제 데이터까지 가지 않아도 되는 경우**를 의미한다.

일반적으로 보조 인덱스로 PK를 찾고, 그 PK로 클러스터형 인덱스를 재탐색하지만 커버링 인덱스는 보조 인덱스에서 끝난다.

예시는 다음과 같다.

```
-- 커버링 O (이름만 필요 → 인덱스에 다 있음)
SELECT name FROM users WHERE name = '김철수';
→ 이름 인덱스만 보고 끝. 데이터 접근 X

-- 커버링 X (나이가 필요 → 인덱스엔 없음)
SELECT name, age FROM users WHERE name = '김철수';
→ 이름 인덱스로 PK 찾고 → 데이터까지 가서 age를 가져와야 함
```

커버링 인덱스는 재탐색을 아예 생략하기 때문에 속도가 많이 빠르다. 특히 조회가 많은 서비스에서 차이가 크다.

**실무에서 복합 인덱스를 만드는 이유도 커버링을 유도**하기 위함이 크다! 복합 인덱스를 만들면 두번째 요소도 커버링이 된다.

<br>

## **인덱스의 단점**

인덱스는 검색 속도를 빠르게 해주지만, 그만큼의 비용이 있다.

### **추가 저장공간**

인덱스는 테이블과 별도로 저장되기 때문에, **추가적인 저장공간**이 필요하다. 인덱스를 많이 만들수록 그만큼 공간을 더 차지하게 된다.

### **쓰기(INSERT, UPDATE, DELETE) 성능 저하**

인덱스는 정렬된 상태를 유지하기 때문에, 인덱스가 많으면, 데이터가 바뀔 때마다 인덱스도 함께 바뀌어야 한다. 그래서 **쓰기 작업이 많을수록 인덱스는 성능 저하**를 유발한다.

```
INSERT → 새 값을 인덱스의 정렬 위치에 삽입 (+ 페이지 분할 가능)
UPDATE → 인덱스 컬럼이 바뀌면 인덱스도 재정렬
DELETE → 인덱스에서도 해당 항목 제거
```

즉, 인덱스는 조회 성능은 높이지만 쓰기 성능을 느리게 한다.
