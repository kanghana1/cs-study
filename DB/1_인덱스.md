# 인덱스 (Index)

## **인덱스란?**

테이블에서 특정 회원을 찾기 위해서는 DB를 첫 줄부터 마지막 줄까지 전부 훑어야 한다. 이를 **풀 테이블 스캔 (Full Table Scan)** 이라고 한다. 이렇게 되면, 데이터가 많을수록 **성능이 나빠**질 수밖에 없다. 이러한 문제를 해결하기 위해 나온 것이 인덱스이다.

인덱스는 책의 **목차**처럼, 특정 데이터를 빠르게 찾을 수 있도록 도와주는 자료 구조이다. 인덱스를 사용하면, DB는 테이블의 모든 데이터를 훑지 않고도 원하는 데이터를 바로 찾을 수 있다.

<br>

## **인덱스의 원리**

인덱스가 빠른 이유는 **데이터가 정렬**되어 있기 때문이다. 이진탐색을 생각하면 된다.

```
정렬 안 됨: [5, 2, 8, 1, 9, 3, 7] → 하나씩 다 비교 (느림)
정렬 됨:    [1, 2, 3, 5, 7, 8, 9] → 범위를 절반씩 좁힘 (빠름)
```

인덱스는 특정 컬럼의 값을 미리 정렬해서 별도로 저장해둔다. 그래서 그 컬럼으로 검색할 때 정렬의 이점을 활용해 빠르게 찾는다.

### **B-Tree 구조**

**B-Tree (정확히는 B+Tree)** 는 **대부분의 DB 인덱스가 쓰는 자료구조**이다.

데이터의 삽입/삭제가 계속 일어나기 때문에 단순 배열이 아닌 트리구조로 이루어져있다.

#### **기본 형태**

```
                [ 50 ]              ← 루트 노드
               /      \
          [20 30]    [70 80]        ← 중간 노드
          /  |  \    /  |  \
        ...  ... ...              ← 리프 노드 (실제 데이터 위치)
```

특징은 다음과 같다.

- **균형 트리(Balanced)**
  - 모든 리프 노드가 같은 높이에 있다.
  - 그래서 어떤 값을 찾든 비슷한 횟수로 도달한다. (검색 성능이 일정하다)
- **탐색 과정**

이렇게 높이가 낮게 유지되기 때문에, 데이터가 많아도 적은 단계로 데이터를 찾을 수 있다.

<br>

#### **B+Tree의 특징**

MySQL을 포함한 실제 DB는 B-Tree를 개선한 B+Tree를 쓴다. B-Tree와의 차이는 다음과 같다.

- **실제 데이터는 리프 노드**에만 있다.
  - 중간 노드는 길을 안내하는 이정표 역할만 한다.
  - 데이터는 전부 맨 아래 리프에 모여있다.

- **리프 노드끼리 연결**되어 있다.
  - 리프 노드들이 서로 링크로 이어져 있어서, **범위 검색에 강하다.**
  - ex| "20 이상 80 이하"를 찾을 때, 20을 찾은 뒤 리프를 따라 옆으로 쭉 읽으면 된다. 다시 위에서부터 탐색할 필요가 없다.

만약 데이터를 삽입할 때 정렬된 상태에서 제각각의 값이 들어온다면 사이를 비집고 들어와야 한다. 이미 꽉 차있으면 **페이지 분할도 필요**하다.

이러한 이유로 **PK는 되도록 순차적으로 증가하는 값**을 쓰는 게 좋다! 여기서 **UUID를 PK로 쓰면 성능이슈**가 있다는 말이 나오는 것이다.

<br>

## **클러스터형 인덱스 VS 보조 인덱스**

인덱스는 크게 두 종류로 나뉜다.

```
클러스터형 인덱스 (Clustered Index)  → 데이터 자체가 정렬됨
보조 인덱스 (Secondary Index)        → 위치만 가리킴
```

이 둘의 차이가 정말 중요하다.
