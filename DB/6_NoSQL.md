# 6. NoSQL 기본

## **관계형 데이터베이스의 한계에 대하여**

우리가 흔히 쓰는 RDB는 데이터 정합성을 보장하고, 정규화로 중복을 없애는 등 정말 좋은 도구이다. 그런데 인터넷 서비스가 커지면서 한계가 드러났다.

### **1. 확장이 어렵다**

RDB는 데이터가 폭증하면 보통 서버 성능 자체를 올리는 방식으로 대응한다. 그러나 이 방법은 한계가 있고 비용이 많이 든다는 문제가 있다. Scale-out을 하기에는 테이블이 JOIN으로 엮여있어 여러 서버로 나누기 쉽지않다.

### **2. 데이터 구조가 유연하지 않다**

RDB는 테이블 구조를 미리 정해야 한다. 요즘 서비스는 데이터 형태가 자주 바뀌기 때문에, 매번 스키마를 바꾸기는 부담이 될 수 있다.

### **3. JOIN이 느리다**

점점 시간이 지날수록 데이터의 양이 방대해지고 있다. 그런데 데이터가 많아지면 JOIN이 느려질 수 있다.

<br>

## **NoSQL이란?**

NoSQL은 Not Only SQL의 약자로, **관계형 모델을 따르지 않는 데이터베이스**를 의미한다.

### **NoSQL 특징**

RDB와 대비되는 특징은 다음과 같다.

#### **유연한 스키마**

NoSQL은 RDB처럼 테이블 구조를 미리 정하지 않아도 된다. 즉, 데이터 구조가 자주 바뀌어도 유연하게 대응할 수 있다.

#### **수평적 확장성**

NoSQL은 서버를 여러 대로 늘리는 Scale-out이 쉽다. 서버를 늘리면 데이터가 자동으로 분산되어 저장된다.

#### **성능이 좋을 수 있다**

NoSQL은 JOIN을 사용하지 않기 때문에, RDB보다 빠른 성능을 낼 수 있다.

다만, 이로인해 ACID 정합성을 일부 포기해야 한다.

<br>

### **NoSQL 종류**

데이터를 저장하는 방식에 따라 크게 4가지로 나뉜다.

#### **1. Key-Value Store**

가장 단순한 형태로 **키 하나에 값 하나를 저장**한다. 구조가 단순해 속도가 빠르고 **캐시나 세션** 저장에 많이 쓴다.

예를 들면 Redis가 있다.

```
"user:1001" → "하나"
"session:abc" → {로그인 정보...}
```

#### **2. Document Store**

**JSON 같은 문서 형태**로 저장한다. 하나의 문서 안에 중첩 구조도 담을 수 있다.

문서마다 필드가 달라도 되어서 유연한 스키마의 장점이 가장 잘 드러난다.

예를 들면 MongoDB가 있다.

```
{
    "id": 1001,
    "name": "하나",
    "courses": ["DB", "알고리즘"]
}
```

#### **3. Column Store**

컬럼 단위로 데이터를 저장한다. RDB처럼 행 단위로 데이터를 저장하는 것이 아니라, **열 단위로 데이터를 저장**한다. 특정 컬럼만 빠르게 읽는 데 유리하고, 대용량 데이터 분석에 유리하다.

예를 들면 Cassandra가 있다.

#### **4. Graph**

그래프 구조로 데이터를 저장한다. 노드와 간선으로 데이터를 표현하며, **관계형 데이터**를 다루는 데 유리하다.

<br>

## **CAP 이론**

CAP 이론은 NoSQL을 이해하는 데 중요한 개념이다. 여러 서버로 나뉜 DB 즉 분산 시스템에서 **세 가지를 동시에 만족할 수 없다는 이론**이다.

### **1. Consistency (일관성)**

데이터를 읽을 때, 모든 서버에서 같은 데이터를 읽을 수 있어야 한다는 의미이다. 즉, **어느 서버에 요청해도 데이터가 항상 최신 값으로 일관된 상태**를 유지해야 한다.

### **2. Availability (가용성)**

데이터를 읽거나 쓸 때, **항상 응답을 받을 수 있어야 한다**는 의미이다. 즉, 서버가 일부 고장나더라도 요청에 대해 응답을 받을 수 있어야 한다.

### **3. Partition Tolerance (분할 내성)**

서버 간 통신이 끊겨도 시스템이 정상 동작해야한다. 즉, 각각의 서버는 살아있지만 **두 서버가 통신할 수 없는 상태더라도 서비스를 지속할 수 있어야** 한다. 단, 이 말이 데이터의 일관성을 유지해야 한다는 의미는 아니다!

<br>

분산 시스템에서는 서버가 여러 대일 때, 중간에 통신이 끊길 가능성은 항상 존재하기 때문에 **네트워크 분할 (P) 는 피할 수 없다.** 이때 가용성과 일관성은 동시에 보장할 수 없어 둘 중 하나를 선택하게 된다.

```
CP 선택 → 일관성 우선 (통신 끊기면, 정확한 값 위해 응답 거부하거나 대기)
          예: 금융, 재고 (틀린 값 주느니 차라리 멈춤)

AP 선택 → 가용성 우선 (통신 끊겨도, 최신 데이터가 아닐 수 있어도 응답은 함)
          예: SNS 피드 (잠깐 옛날 값이어도 일단 보여줌)
```

운영하는 서비스의 성격에 따라 선택하면 된다.

<br>

## **SQL과 NoSQL 중 무엇을 선택해야할까?**

결론적으로 말하면 데이터의 정합성, 관계가 중요하다면 RDB를, 대용량 고속 처리와 유연한 구조가 중요하면 NoSQL을 선택하는 게 좋다.

실무에서는 보통 RDB와 NoSQL을 함께 사용한다!
