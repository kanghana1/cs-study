# 3. 스레드 동기화

같은 프로세스 내 스레드는 스택을 제외한 힙, 데이터, 코드 영역을 공유한다. 이렇게 메모리를 공유하게 되면 동시에 작성하고 동시에 읽는 작업이 일어날 수 있고, 이로 인해 데이터의 정합성이 깨지게 된다. 이러한 이유로 **스레드 동기화**가 필요하다.

<br>

## ✅ 임계 구역 (Critical Section)

임계 구역이란, 공유 데이터에 접근하는 코드 구간을 의미한다. 즉 동시에 실행될 경우 데이터 정합성이 깨질 수 있는 구간이다.

```
int count = 0; // 공유 데이터

void increment() {

  // 임계구역 시작
  count = count + 1;
  // 임계구역 종료
}
```

위 코드는 우리의 입장에서는 count = count + 1 한 줄이지만, 실제로 연산과정은 다음과 같다.

1. count 읽기
2. +1 연산하기
3. count 쓰기

이 과정은 충분히 끊길 수 있고, 데이터의 정합성을 위해서는 끊겨서는 안 되는 구간이다. 임계 구역이 보호되지 않으면 **Race Condition** 이 발생한다.

<br>

> **🔗 경쟁조건 (Race Condition)**
>
> 여러 스레드가 공유 데이터에 동시에 접근할 때 실행 순서에 따라 결과가 달라지는 현상

<br>

### 임계구역 보호

임계구역을 제대로 보호하기 위한 조건은 다음과 같다.

<br>

**1. 상호 배제 (Mutual Exclusion)**

한 스레드가 임계 구역을 실행중이면 다른 스레드가 절대 들어올 수 없다.

**2. 진행**

임계구역을 실행중인 스레드가 없으면 임계 구역에 들어가길 원하는 스레드는 반드시 들어갈 수 있다.

**3. 한계 대기 (Bounded Waiting)**

기다리는 스레드가 무한정 기다리면 안 된다.

<br>

<hr>

## ✅ 스레드 동기화 도구

이렇게 임계 구역을 보호하기 위한 도구에는 **뮤텍스, 세마포어, 모니터** 등이 있다.

<br>

### **1. 뮤텍스 (Mutex)**

Mutual Exclusion의 줄임말로 열쇠가 1개인 자물쇠라고 이해하면 된다. 즉 **하나의 스레드**만 임계 구역에 접근할 수 있도록 하는 동기화 도구이다.

**동작 방식**

```
1. 스레드가 임계 구역이 진입 전 lock()을 호출
2. 다른 스레드가 lock()을 호출할 때, 이미 잠겨있다면 대기
3. 임계 구역 실행이 완료되면 unlock()을 호출
4. 대기중인 스레드가 lock()을 획득해 진입
```

lock을 건 스레드만 unlock 할 수 있는 구조이다.

<br>

### **2. 세마포어 (Semaphore)**

열쇠가 N개인 자물쇠라고 생각하면 된다. 즉, 동시에 접근할 수 있는 **스레드의 개수를 제한**한다. 여기서 개수는 개발자가 지정하며, 지정하는 기준은 **Race Condition이 발생하지 않는 수준**으로 정한다.

예를 들어 DB 커넥션 풀에서 커넥션이 3개라면, 독립적으로 한 개씩 사용이 가능하기 때문에 3개까지는 괜찮다.

**동작 방식**

```
S = 3 (열쇠 3개로 시작)

스레드 진입 시 → wait()  : S를 1 감소 (S == 0이면 대기)
스레드 퇴장 시 → signal(): S를 1 증가 (대기 중인 스레드 깨움)
```

<br>

**세마포어 종류**

**1. 이진 세마포어 (Binary Semaphore)**

S = 1 인 세마포어로 **뮤텍스와 동일**하게 동작한다.

**2. 카운팅 세마포어**

S가 2 이상인 세마포어

<br>

**세마포어 대기방식**

세마포어는 어떻게 대기하고, 임계구역에 진입할 수 있게 될까? 세마포어의 대기 방식은 크게 두가지이다.

**1. Busy Waiting**

사용 가능한 자원이 없는 경우 계속 상태를 확인하면서 기다리는 방식이다. 이 방식은 계속 CPU를 점유하면서 대기하기 때문에 CPU가 낭비될 수 있다. 대신 대기 시간이 짧으면 빠르게 진입할 수 있다는 장점이 있다.

**2. Block & Wakeup**

사용 가능한 자원이 없는 경우 대기 큐에 들어가서 잠들고 (wake), 작업을 끝낸 다른 스레드가 signal을 호출하면서 깨우는 방식이다. CPU를 낭비하지 않는다는 장점이 있으나, 잠에 들고 꺠우는 과정에서 오버헤드가 발생할 수 있다.

> **🔗 Block & Wakeup 방식의 오버헤드**
>
> 잠들고 깨우는 과정에서의 오버헤드는 OS가 개입한다는 점에 있다. 스레드가 잠에 들어 스레드를 대기 큐에 넣게 되면 스레드의 상태를 **Running -> Waiting으로 변경**하게 되고, 이후 다른 스레드로 전환하면서 **Context Switching**이 발생한다.
>
> 깨울 때에도 마찬가지로 대기 큐에서 꺼내고, 스레드의 상태를 **Waiting -> Ready로 변경**한다. 이렇게 **Context Switching**이 발생하게 되고, 이러한 과정에서 오버헤드가 발생한다.

그렇기 때문에, 대기 시간이 짧을 것으로 예상되는 경우에는 Busy Waiting이, 길 것으로 예상되는 경우에는 Block & Wakeup이 좋은 선택이 될 수 있다!

<br>

### **Mutex lock vs Semaphore**

- Mutex는 lock을 건 스레드가 unlock을 할 수 있다. 즉 소유권이 현재 실행중인 스레드에 있다.
- 세마포어는 다른 스레드가 signal()을 호출할 수 있다.

<br>

### **3. 모니터 (Monitor)**

모니터는 뮤텍스를 좀 더 편리하고 안전하게 쓸 수 있도록 만든 고수준 동기화 도구이다.

뮤텍스는 개발자가 직접 lock/unlock 하는 과정에서 실수를 할 수 있으나, 모니터는 이런 실수를 방지해준다.

대표적인 예시로는 Java의 **synchronized** 키워드가 있다!

> **🔗 자바의 synchronized에 대하여**
>
> synchronized는 메서드에 붙일 수 있고, 메서드 내 블럭을 지정하는 방식으로도 사용할 수 있다.
>
> ```
> // 메서드에 붙이기
> public synchronized void increment() {
>    System.out.println("시작");  // >얘도 임계 구역에 포함됨 (불필요)
>    count = count + 1;
>    System.out.println("끝");   // 얘도 임계 구역에 포함됨 (불필요)
> }
>
> // 블록에 붙이기
> public void increment() {
>     System.out.println("시작");
>     synchronized (this) {
>       count = count + 1;
>     }
>     System.out.println("끝");
> }
> ```
>
> 임계구역은 좁을수록 좋기 때문에, 블록에 붙이는 것처럼 필요한 부분에만 붙이는 것이 좋다! **private 메서드**로 분리해서 사용하는 것도 좋아보인다.
>
> **synchronize**는 \*\*객체단위로 모니터 잠금이 진행되기 때문에 같은 객체 사이에서 모니터를 공유한다.
>
> 그래서 static 필드가 있는 경우를 주의해야 하는데, static 필드는 객체가 아닌 **클래스 단위의 변수**이기 때문에 보호가 되지 않는다. static 필드를 다뤄야 하는 경우에는 **클래스 단위로 모니터 잠금**이 되는 **static synchronize**를 사용해야 한다.
>
> 단, static synchronize를 많이 사용하게 되면 자바의 멀티스레드가 자칫 **싱글 스레드**처럼 돌아가게 되므로 주의해야한다! (간단한 연산의 경우는 **Atomic 객체**를 사용하는 것이 좋다.)
