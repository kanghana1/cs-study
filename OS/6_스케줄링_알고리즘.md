# 6. 스케줄링 알고리즘

단기 스케줄러가 Ready Queue에서 누구에게 CPU를 줄지 결정하는 방법을 스케줄링 알고리즘이라고 한다. CPU를 할당할 때 성능이 중요한 기준이 된다.

<br>

## **성능 측정 기준**

**1. 대기시간 (Waiting Time)**

Ready Queue에서 기다린 시간

**2. 반환 시간 (Turnaround Time)**

프로세스 시작부터 완료까지 걸린 전체 시간

**3. 응답 시간 (Response Time)**

요청 후 첫 번째 응답이 올 때까지 걸린 시간

<br>

## **스케줄링 알고리즘 종류**

### **✅ 1. FCFS (First Come First Served)**

말 그대로 먼저 온 프로세스를 먼저 실행하는 가장 단순한 알고리즘이다.

실행시간이 짧은 프로세스가 늦게 들어왔을 때, 짧은 일을 처리하기 위해 긴 시간을 대기해야 하므로 비효율적이다.

**예시**

```
P1 실행시간 24ms
P2 실행시간 3ms
P3 실행시간 3ms

실행 순서: P1 → P2 → P3

P1: 0ms에 시작, 24ms에 끝 -> 대기시간 0ms
P2: 24ms에 시작, 27ms에 끝 -> 대기시간 24ms
P3: 27ms에 시작, 30ms에 끝 -> 대기시간 27ms

평균 대기시간: (0 + 24 + 27) / 3 = 17ms
```

이처럼 실행 시간이 긴 프로세스가 CPU를 점유하는 동안, 뒤에 대기 중인 짧은 프로세스들이 전부 오래 기다려야 하는 현상을 **호위효과(Convoy Effect)** 라고 한다.

<br>

**FCFS 특징**

- **비선점 방식** - CPU를 한 번 할당 받으면 끝날때까지 뻇기지 않음
- **Convoy Effect**로 대기시간이 길어질 수 있음

<br>

### **✅ 2. SJF (Shortest Job First)**

이름 그대로 실행시간이 짧은 프로세스를 먼저 실행하는 알고리즘으로, FCFS의 Convoy Effect를 해결하기 위해 나온 방식이다.

**예시**

```
P1 실행시간 6ms
P2 실행시간 8ms
P3 실행시간 7ms
P4 실행시간 3ms

실행 순서: P4(3) → P1(6) → P3(7) → P2(8)

P4: 대기시간 0ms
P1: 대기시간 3ms
P3: 대기시간 9ms
P2: 대기시간 16ms

평균 대기시간: (0 + 3 + 9 + 16) / 4 = 7ms
```

SJF가 이론적으로는 최적이지만, 몇가지 현실적인 문제가 있다.

1. 실행시간을 미리 알 수 없다.
2. 실행시간이 긴 프로세스는 영원히 CPU를 할당받지 못하는 기아현상이 생길 수 있다.

<br>

**SJF 특징**

- **비선점 방식** - CPU를 한 번 할당 받으면 끝날때까지 뻇기지 않음
- 다른 프로세스가 먼저 도착했어도 실행시간이 짧은 프로세스에게 우선 할당
  - 이로인해 **기아 현상(Starvation)** 이 발생할 수 있음

<br>

### **✅ 3. SRTF (Shortest Remaining Time First)**

SJF의 선점 버전으로, 남은 실행시간이 더 짧은 프로세스가 CPU를 할당받는 방법이다. 실행하다가도 남은 실행시간이 더 짧은 프로세스가 새로 도착하면 즉시 CPU를 빼앗길 수 있다.

**예시**

```
P1 도착 0ms, 실행시간 8ms
P2 도착 1ms, 실행시간 4ms

0ms: P1 실행 시작 (남은시간 8ms)
1ms: P2 도착 (남은시간 4ms) → P1 남은시간 7ms보다 짧음
     -> P1에서 CPU 빼앗아 P2 실행
5ms: P2 종료 -> P1 다시 실행
13ms: P1 종료
```

<br>

**SRTF 특징**

- **선점 방식**
- 새로운 프로세스가 도착할 때마다 남은 실행시간 비교
- SJF보다 **Starvation**이 심함
- 교체가 자주 일어나다보니 **Context Switching으로 인한 오버헤드**가 큼

<br>

### **✅ 4. RR (Round Robin)**

모든 프로세스에게 동일한 Time Quantum을 주고, 시간이 끝나면 다음 프로세스에게 CPU를 넘기는 방식이다. 모든 프로세스가 공평하게 같은 시간을 할당받기 때문에 공평성이 가장 좋다.

**예시**

```
Time Quantum = 4ms
P1 실행시간 10ms, P2 실행시간 4ms, P3 실행시간 6ms

0ms  ~ 4ms  : P1 실행 (남은시간 6ms)
4ms  ~ 8ms  : P2 실행 (남은시간 0ms) → P2 종료
8ms  ~ 12ms : P3 실행 (남은시간 2ms)
12ms ~ 16ms : P1 실행 (남은시간 2ms)
16ms ~ 18ms : P3 실행 (남은시간 0ms) → P3 종료
18ms ~ 20ms : P1 실행 (남은시간 0ms) → P1 종료
```

 <br>

**RR 특징**

- **선점** 방식
- 모든 프로세스가 공평하게 CPU 할당
- **Starvation**이 발생하지 않음
- **time quantum의 크기**가 정말 중요함

<br>

> **🔗 time quantam 크기에 따른 성능**
>
> Round Robin은 time quantam의 크기에 따라 성능이 완전히 달라진다.
>
> **1. Time Quantam이 너무 큰 경우**
>
> 프로세스가 끝날 때까지 오래 기다려야해서 FCFS랑 다를게 없어짐
>
> **2. Time Quantam이 너무 작은 경우**
>
> Context Switching이 너무 자주 일어나서 오버헤드가 폭증해 비효율적
>
> -> 그래서 보토은 10~100ms로 설정하는게 일반적

이렇게 적당한 Time Quantam을 설정하는 게 어렵다는 문제가 있다!

그리고 현실에서는 프로세스마다 중요도가 다르기 때문에, 공평함이 오히려 비효율적일 수 있다.

예를 들면, 게임 프로세스와 백신 업데이트 프로세스가 있을 때 이 둘을 똑같이 대우하게 되면 사용자 입장에서는 게임이 버벅이는 것처럼 느낄 수 있다.
