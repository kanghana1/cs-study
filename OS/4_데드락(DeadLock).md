# 4. 데드락 (Deadlock)

스레드의 동기화가 필요하다는 것을 알았다. 그러나, 동기화 도구를 잘못 사용했을 때 생길 수 있는 문제가 있다. 예를 들면 아래와 같은 상황이다.

```
스레드1과 스레드2가 자원 1,2를 모두 얻어야 하는 상황이다.

1. 스레드 1이 자원 1을 얻는다.
2. 스레드 2가 자원 2를 얻는다.
3. 스레드 1이 자원 2를 기다린다.
4. 스레드 2가 자원 1을 기다린다.

-> 서로 원하는 자원이 상대에게 할당되어 있기 때문에 두 스레드는 무한정 대기 상태에 빠진다.

```

위처럼 두 개 이상의 주체가 서로 상대방의 자원을 기다리며 **무한정 대기하는 상태**를 **데드락**이라고 한다.

데드락은 스레드에 국한되는 개념이 아니라, 프로세스, 데이터베이스 등 다양한 상황에서 발생하는 문제점이다! 문제가 발생하는 이유는 동일하기 때문에, 지금은 스레드를 예시로 설명하려고 한다.

<br>

## **✅ Deadlock 발생 조건 4가지**

Deadlock은 아래 **4가지가 동시에 만족**할 때 발생한다. 하나라도 깨지면 발생하지 않는다.

**1. 상호 배제**

자원을 한 번에 하나의 스레드만 사용 가능한 경우

사실 동기화의 특성상 상호 배제는 거의 만족한다.

> **🔗 상호배제가 깨지는 경우**
>
> 자원을 읽기만 하는 경우에는하나의 자원을 여러 스레드가 사용할 수 있기 때문에 상호 배제 조건이 성립하지 않아 데드락이 발생하지 않는다!

**2. 점유와 대기 (Hold and Wait)**

자원을 점유한 채로 다른 프로세스에 할당되어 사용중인 자원을 기다리는 경우

**3. 비선점 (No preemption)**

다른 스레드가 사용중인 자원을 강제로 빼앗을 수 없는 경우

**4. 순환 대기(Circular Wait)**

순환 형태로 자원을 대기하고 있는 경우

<br>

## **✅ Deadlock 예방 & 회피**

### **1. 예방 (prevention)**

데드락 상태 발생 조건 중 하나를 제거하면서 해결하는 방식으로 설계 단계에서 교착 상태에 빠질 수 있는 조건 자체를 제거하는 방식이다.

조건 중 상호 배제는 제거가 어렵기 때문에 나머지 3가지 조건 중 하나를 제거해서 해결한다. 단, 해결 과정을 보면 자원 낭비가 심하다는 것을 알 수 있다.

<br>

**ㄱ. 점유와 대기 제거**

한 개를 가진 채로 다른 이용중인 자원을 서로 기다려서 발생하기 때문에,

1. 필요한 자원을 한꺼번에 요청하거나 (하나라도 없으면 시작 X),
2. 중간에 못얻으면 기존에 갖고있던 자원을 반납해서 **점유한 채로 대기하는 상황을 제거**

함으로써 해결할 수 있다.

1번의 경우 당장 필요하지 않은 자원까지 점유하게 되고, 이로 인해 다른 스레드도 사용할 수 없게 되어 자원낭비가 발생할 수 있다.

2번의 경우 특정 스레드가 계속 반납만 하게 되면, 영원히 실행되지 못하는 **Starvation(기아)** 상태에 빠지게 된다.

> 기아 상태는 **스케줄링**을 통해 오래 작업하지 못한 스레드의 우선순위를 올려 작업하는 방식으로 해결할 수 있다! **(Aging)**

<br>

**ㄴ. 비선점 제거**

자원을 뻇지 못하고 대기해야 하기 때문에 교착 상태에 빠지므로 자원을 강제로 빼앗을 수 있게 하여 해결한다.

이 경우, 원래 작업하던 스레드의 중간 결과가 날아갈 수 있고 날아가면 했던 작업을 다시 해야하므로 자원이 낭비된다.

(TCB에는 PC, 레지스터 등 CPU 상태가 저장되는 거라서 가공한 결과물은 날아갈 수 있다!)

<br>

**ㄷ. 순환 대기 제거**

순환 대기로 인해 교착 상태가 발생하므로 자원에 번호를 매겨 항상 그 순서대로만 요청하도록 하여 해결한다.

이 경우, 필요 없는 자원까지 요청해서 순서대로 받아야 하기 때문에 자원 낭비가 발생한다.

<br>

### **2. 회피 (avoidance)**

예방과 달리 실행 중에 자원을 줘도 안전한지를 미리 계산하고 결정하는 방식이다.

안전한지 상태 여부에 따라 안전 상태와 불안전 상태로 구분할 수 있다.

<br>

**1. 안전상태**

현재 자원 배분 상태에서 모든 스레드가 언젠가는 반드시 실행이 완료될 수 있는 상태를 의미한다.

모든 경우가 안전한 걸 의미하는 건 아니고, **안전 순서가 존재하는가?** 로 결정한다.

**2. 불안전상태**

어떤 순서로도 모든 스레드가 완료될 수 없어 Deadlock이 발생할 가능성이 있는 상태를 의미한다.

<br>

**✔️ 회피 방식 - 은행원 알고리즘 (Banker Algorithm)**

프로세스가 자원을 요구할 때, 시스템(OS 자원관리자)은 자원을 할당한 후에도 안정 상태로 남아있게 되는지 사전에 검사하여 교착 상태 회피하는 알고리즘이다.

단, 이 알고리즘에는 다음과 같은 문제가 있다.

1. 스레드 수, 자원 수를 미리 알아야 한다.
   -> 실제 시스템에서는 예측이 불가능
2. 매번 안전 상태를 계산하기 때문에 오버헤드가 발생할 수 있다.
3. 자원 수가 고정되어 있어야 한다. (동적이면 사용이 힘듦)

따라서 실제 상황에서는 사용이 힘들다.

<br>

### **3. 탐지 & 회복 (Detection & Recovery)**

예방과 회피는 교착 상태에 빠지지 않도록 막는 게 목적이었다면, 탐지&회복은 교착 상태에 빠졌을 때 어떻게 해결할지에 초점을 맞춘다는 차이가 있다.

<br>

**탐지 (Detection)**

주로 자원 할당 그래프를 통해 교착 상태를 탐지한다.

**자원할당 그래프**란, 어떤 스레드가 어떤 자원을 점유하고 있고, 어떤 자원을 대기하고 있는지 시각적으로 나타낸 방향 그래프이다.

**사이클이 존재**하는지를 확인하여 교착 상태를 탐지할 수 있다!

탐지 주기는 아래 세 가지 경우가 있다. 탐지 주기는 OS설계자나 시스템 관리자가 결정하며, 표준은 없다.

**1. 자원 요청이 실패할 때마다 실행**
→ 정확하지만 오버헤드 큼

**2. 주기적으로 실행 (1분마다 등)**
→ 오버헤드 적지만 탐지가 늦을 수 있음

**3. CPU 사용률이 낮아질 때 실행**
→ Deadlock이 생기면 CPU가 놀기 때문

<br>

**회복 (Recovery)**

교착 상태 탐지 후 해결하는 방법이다. 방법은 크게 두 가지가 있다.

<br>

**1. 프로세스/스레드 강제 종료**

- 관련된 스레드를 전부 종료한다. 확실하게 해결이 가능하지만, 작업이 날아갈 수 있다.

- 스레드를 하나씩 종료하면서 Deadlock이 풀리는지 확인한다. 탐지를 반복해야 한다는 단점이 있다.

**2. 자원 강제 선점**

Deadlock에 걸린 스레드에서 자원을 강제로 빼앗아 다른 스레드에 할당한다. 뻇긴 스레드는 롤백하고 자원을 받은 스레드는 실행을 계속한다.

뺴앗았을 때 영향이 가장 적은 자원, 혹은 롤백 비용이 가장 적은 스레드의 자원을 선점하여 피해를 최소화한다.

이때도 매번 같은 스레드가 희생하게 되면 **Starvation (기아)** 가 발생할 수 있다.

## **✅ 관련된 고전 문제들**

<br>

### **1. 생산자-소비자 문제 (Producer-Consumer Problem)**

데이터를 생산하는 쪽과 소비하는 쪽이 있을 때, 각각을 **생산자와 소비자**라고 하고 이때 둘 사이의 공유공간을 **버퍼**라고 한다.

생산자와 소비자가 같은 속도로 데이터를 생산하고 소비한다면 문제가 되지 않지만, 서로 다른 속도로 동작한다고 생각하면 다음과 같은 문제가 발생한다.

- 생산자가 빠른 경우 -> 버퍼가 꽉 참
- 소비자가 빠른 경우 -> 버퍼가 비어서 꺼낼 데이터가 없음

또, 버퍼는 공유메모리이기 때문에 생산자가 넣는 동시에 소비자가 꺼내면 **Race Condition**이 발생한다.
이를 해결하기 위해 **3개의 세마포어**를 이용한다.

<br>

**1. 버퍼가 꽉 찼을 때 - 생산자 대기**

```
empty → 버퍼의 빈 공간 개수를 나타냄

생산자가 넣으려면 → 빈 공간이 있어야 함
빈 공간이 없으면  → 생산자는 대기

=> 소비자가 꺼내면 → 빈 공간이 생김 → 생산자 깨어남
```

<br>

**2. 버퍼가 비었을 때 - 소비자 대기**

```
full → 버퍼에 찬 공간(데이터) 개수를 나타냄

소비자가 꺼내려면  → 데이터가 있어야 함
데이터가 없으면    → 소비자는 대기

=> 생산자가 넣으면 → 데이터가 생김 → 소비자 깨어남
```

<br>

**3. 동시 접근 방지**

```
mutex → 버퍼 자체를 잠그는 용도

생산자나 소비자 중 하나가 버퍼 접근 중이면
→ 다른 쪽은 대기
→ Race Condition 방지
```

즉, 세 개의 세마포어 (empty, full, mutex) 가 각각 생산자, 소비자, 동시접근을 제어해서 race condition을 방지한다!

<br>

### **2. 독자-저자 문제 (Readers-Writers Problem)**

생산자-소비자 문제와 달리 독자-저자 문제는 저자가 데이터를 읽기만 하기 때문에, 저자에 대한 제어는 불필요하게 성능을 낭비하는 일이 된다.
해당 문제의 경우 **2개의 세마포어**를 사용한다.

- **mutex** : 독자 수 수정용
- **rw_mutex** : 저자가 쓸 때 혹은 첫/마지막 독자가 접근시 잠금용

<br>

**1. 독자 수 수정**

독자가 첫번째 독자면 저자가 들어오지 못하게 lock을 걸고, 독자는 들어올 수 있게 한다. 마지막 독자가 나갈 때에는 저자가 들어올 수 있도록 락을 풀어준다.

<br>

**코드 흐름 - 독자 ver**

```
wait(mutex)         → read_count 수정 잠금
read_count + 1      → 독자 1명 추가
if read_count == 1  → 첫 번째 독자면
    wait(rw_mutex)  → 저자 못 들어오게 잠금
signal(mutex)       → read_count 수정 잠금 해제

데이터 읽기

wait(mutex)         → read_count 수정 잠금
read_count - 1      → 독자 1명 감소
if read_count == 0  → 마지막 독자면
    signal(rw_mutex)→ 저자 들어올 수 있게 잠금 해제
signal(mutex)       → read_count 수정 잠금 해제
```

<br>

**코드 흐름 - 저자 ver**

```
wait(rw_mutex)  → 독자/저자 전부 못 들어오게 잠금
데이터 수정
signal(rw_mutex)→ 잠금 해제
```

사실 위의 문제점은 독자가 끊임없이 들어올 때이다. 독자가 끊임없이 들어오면 저자는 영원히 대기하는 **기아상태(starvation)**에 빠질 수 있다는 문제가 있다. 이는 반대의 경우에도 마찬가지이다.

> **그렇다면 실제 데이터베이스에서는 어떻게 이 문제를 해결할까?**
>
> 이 부분은 DB파트에서 다룰거라 간단하게만 짚으려 한다.
>
> DB는 트랜잭션마다 격리 수준을 설정해서 **읽기 전용 트랜잭션**은 **동시에 여럿**이 가능하게 하고, **쓰기 트랜잭션**은 **격리 수준**에 따라 제어한다.
>
> - 격리수준이 높다 -> 동시 접근을 적게 허용 (안전하고 느림)
> - 격리수준이 낮다 -> 동시 접근을 많이 허용 (빠르고 위험)

<br>

### **2. 식사하는 철학자 문제 (Dining Philosophers Problem)**

이 문제도 유명한 문제이다. 원형 테이블에 앉은 철학자들 사이마다 젓가락 1개씩 (총 5개) 가 있다.

철학자는 생각하거나, 먹거나 둘 중 한가지만 할 수 있고, 밥을 먹기 위해서는 왼쪽 젓가락, 오른쪽 젓가락 2개가 모두 필요하다.

이 문제에서 철학자 모두가 밥을 먹기로 하고 자신의 오른쪽 젓가락을 먼저 집으면 **Deadlock** 상태가 발생하게 된다. (순환대기)

<br>

이 교착상태는 다음과 같이 해결할 수 있다.

1. n명이 앉을 수 있는 테이블에서 철학자를 n-1명만 앉힘 (세마포어)

2. 한 철학자가 젓가락 두개를 모두 집을 수 있는 상황에서만 젓가락 집도록 허용 (점유와 대기 조건 제거)
   -> 이 경우는 **starvation** 가능성이 있다!

3. 누군가는 왼쪽 젓가락을 먼저 집지 않고 오른쪽 젓가락을 먼저 집도록 허용 (순환대기 제거)
