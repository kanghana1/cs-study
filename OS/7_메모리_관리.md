# 7. 메모리 관리 전략

## **메모리 할당이 필요한 이유**

각각의 프로세스는 독립된 메모리 공간을 갖고, OS 또는 다른 프로세스의 메모리 공간에 접근할 수 없다. (**단, OS는 운영체제 메모리영역과 사용자메모리영역 접근에 제약이 없다.**)

여러 프로세스가 동시에 실행되는 환경에서 OS는 각 프로세스에게 메모리를 어떻게 나눠줄지 결정해야한다. 할당 방식은 크게 **연속 할당**과 **불연속 할당**으로 나눌 수 있다.

<br>
<hr>

## **✔️ 연속 할당(Contiguous Allocation)**

프로세스를 메모리의 연속된 공간에 통째로 올리는 방식이다. 연속된 메모리를 어떻게 할당해주냐에 따라 **고정 분할**과 **가변 분할**로 다시 한 번 나눌 수 있다.

<br>

### **고정 분할 (Fixed Partition)**

메모리를 **미리 고정된 크기**로 나눠놓고, 프로세스가 오면 그 칸에 넣는 방식이다.

<br>

**문제점 - 내부 단편화**

고정된 크기로 메모리를 쪼개두다보니, 프로세스 크기가 파티션의 크기와 딱 맞는 경우가 거의 없다. 예를 들어 80MB짜리 프로세스가 100MB짜리 파티션에 들어갈 경우 20MB가 낭비된다.

이렇게 **파티션 내에 사용하지 못하는 공간이 생기는 것**을 내부 파편화라고 한다. 내부 파편화가 발생할 경우, 낭비되는 메모리가 많아진다는 문제가 있다.

<br>

### **가변 분할 (Variable Partition)**

가변 분할은 프로세스 크기에 맞게 **메모리를 동적으로 나눠**주는 방식으로, 고정 분할의 내부 단편화 문제를 해결할 수 있다.

```
초기 상태         P1(100MB) 할당    P2(50MB) 할당
┌──────────┐     ┌──────────┐     ┌──────────┐
│          │     │    P1    │     │    P1    │
│  300MB   │ →   │  100MB   │ →   │  100MB   │
│  (빈공간) │     ├──────────┤     ├──────────┤
│          │     │          │     │    P2    │
│          │     │  200MB   │     │   50MB   │
└──────────┘     │  (빈공간) │     ├──────────┤
                 └──────────┘     │  150MB   │
                                  │  (빈공간) │
                                  └──────────┘
```

내부 단편화는 없어졌지만, 메모리 할당을 해제할 때 새로운 문제가 생긴다.

<br>

**문제점 - 외부 단편화**

프로세스들이 할당되고 해제되다보면, 빈 메모리 공간이 여기저기 흩어져서 생긴다.

예를 들어, 각각 100MB와 70MB의 메모리 해제가 일어난 경우, 빈 메모리는 170MB지만, 연속된 공간이 아니기 때문에 120MB짜리 프로세스는 할당할 수 없게 된다.

이러한 경우를 **외부 단편화**라고 한다. 외부 단편화를 해결하기 위해 **압축** 기법을 사용한다.

> **🔗 압축**
>
> 흩어진 빈 공간을 한 쪽으로 모아주는 기법으로 빈 공간이 합쳐져 외부 단편화를 해결할 수 있다.
>
> 그러나, 프로세스를 통째로 이동시켜야 하기 때문에 **오버헤드가 엄청 커져** 근본적인 해결책이라고 할 수 없다.

<br>

프로세스를 연속된 메모리에 올리려 하다보니 위와 같은 문제가 발생하게 되는 것이다. 만약 **프로세스를 잘게 쪼개서 흩어진 빈 공간에 나눠담는다**면 이 문제를 해결할 수 있지 않을까? 여기서 불연속 할당 아이디어가 나왔다.

<br>
<hr>

## **✔️ 불연속 할당(Non-Contiguous Allocation)**

불연속 할당의 대표적인 방법에는 페이징과 세그멘테이션이 있다.

<br>

### **페이징(Paging)**

페이징은 두 가지 공간을 다룬다.

- **논리 주소 공간 (프로세스)** : **페이지**라는 고정 크기 단위로 자름
- **물리 메모리**: **프레임**이라는 동일한 크기의 단위로 자름

이때 페이지와 프레임은 크기가 같고, 보통 **4KB**를 많이 사용한다! 예를 들어 프로세스의 0번 페이지가 물리메모리 7번 프레임에, 1번 페이지가 4번 프레임에 들어가도 문제가 없다.

```
프로세스 A (논리 주소 공간)        물리 메모리 (프레임)
┌──────────┐                      ┌──────────┐
│ Page 0   │ ──────────┐          │ Frame 0  │ ← 다른 프로세스
├──────────┤           │          ├──────────┤
│ Page 1   │ ───────┐  └────────→ │ Frame 1  │ ← A의 Page 0
├──────────┤        │             ├──────────┤
│ Page 2   │ ────┐  └───────────→ │ Frame 2  │ ← A의 Page 1
└──────────┘     │                ├──────────┤
                 │                │ Frame 3  │ ← 다른 프로세스
                 └──────────────→ │ Frame 4  │ ← A의 Page 2
                                  └──────────┘
```

**페이지 테이블 (Page Table)**

대신 어떤 페이지가 어떤 프레임에 들어갔는지를 알아야 하기 때문에, 이를 기록해두어야 한다. 이를 **페이지 테이블(Page Table)** 이라고 한다.

페이지 테이블은 **페이지와 프레임을 매핑한 테이블**이고, 프로세스마다 각각 한 개씩 가지고 있다!

<br>

**주소 변환**

CPU가 쓰는 주소와 실제 메모리 주소는 다르다. CPU는 논리주소를 쓰고 실제 메모리는 물리주소를 쓰는데, 이걸 변환해주는 하드웨어가 바로 **MMU(Memory Management Unit)** 이다.

<br>

**논리주소**는 **페이지번호와 오프셋**으로 나뉘는데, **페이지 번호**는 **몇 번쨰 페이지**인지를, **오프셋**은 **그 페이지 안에서 몇 번째 위치**인지를 나타낸다.

```
논리 주소 = [ 페이지 번호 (p) | 오프셋 (d) ]
```

변환 과정은 아래와 같다.

1. 논리 주소를 **p (페이지 번호)와 d (오프셋)**로 분리
2. 페이지 테이블에서** p로 프레임 번호(f)를 찾음**
3. **물리 주소 = [ 프레임 번호(f) | 오프셋(d) ]**

메모리에 접근할 때마다 위 변환과정을 진행한다!

<br>

#### **페이징의 장단점**

**장점**

- 페이지랑 프레임 크기가 같아서, 빈 프레임이 어디에 있든 그냥 페이지를 넣을 수 있음
- 흩어진 빈 공간 문제가 사라짐

**단점**

- 내부 단편화가 여전히 조금 남음

  - 프로세스 크기가 페이지 크기의 배수로 떨어지지 않는이상 마지막 페이지에 빈 공간이 생김

- 페이지 테이블 접근 비용 존재
  - 프레임 번호를 찾을 때, 실제 데이터를 읽을 때 이렇게 두 번 메모리 접근이 일어남
  - 이러한 성능 부담을 해결하기 위해 **TLB라는 캐시**를 이용함

<br>

### **세그멘테이션 (Segmentation)**

페이징의 문제점은 프로그램의 의미를 전혀 고려하지 않는다는 점이다. 코드, 데이터 등 논리적 경계를 무시하고 그냥 페이지 크기에 맞게 잘라버린다.

이와 달리 세그멘테이션은 아래 그림처럼 프로세스를 의미있는 논리적 단위로 자른다.

```
프로세스
┌──────────┐
│  Code    │ → Segment 0
├──────────┤
│  Data    │ → Segment 1
├──────────┤
│  Heap    │ → Segment 2
├──────────┤
│  Stack   │ → Segment 3
└──────────┘
```

대신 각 세그먼트의 크기는 다 제각각이다!

<br>

**세그먼트 테이블 (Segment Table)**

아까 페이지테이블은 크기가 다 같기 때문에, 위치만 저장하면 되었지만, **세그먼트 테이블**의 경우 크기가 다 다르기 때문에 **시작위치와 크기까지 저장**해야 한다.

```
세그먼트 테이블
┌────────┬─────────┬─────────┐
│ 세그먼트│  base   │  limit  │
├────────┼─────────┼─────────┤
│   0    │  1400   │   400   │ ← Code: 1400번지부터 400 크기
│   1    │  6300   │   200   │ ← Data: 6300번지부터 200 크기
│   2    │  4300   │  1100   │ ← Heap
│   3    │  3200   │  1000   │ ← Stack
└────────┴─────────┴─────────┘
```

<br>

**주소 변환**

논리 주소는 페이징이랑 비슷하게 두 부분으로 나눈다.

```
논리 주소 = [ 세그먼트 번호 (s) | 오프셋 (d) ]
```

변환 과정도 비슷한데, 2번을 주의깊게 봐야한다.

1. 세그먼트 번호(s)로 테이블에서 **base와 limit**를 찾음
2. **오프셋(d)이 limit보다 작은지 검사**
3. 물리 주소 = base + d

오프셋이 limit보다 크면, 다른 세그먼트 영역을 침범하기 때문에 에러를 낸다!

<br>

#### **세그멘테이션의 장단점**

**장점**

- 논리적 단위로 나뉘기 때문에 여러 프로세스의 **코드 공유가 쉬워짐**
  - 같은 코드를 두 번 실행하는 경우 data, heap, stack은 달라지지만, code 부분은 재사용이 가능함!

**단점**

- 세그먼트 크기가 제각각이라 **외부 단편화 문제**가 남음

<br>

> **🔗 현대 방식**
>
> 현대 OS는 보통 페이징을 기본으로 쓰고, 세그멘테이션의 장점(논리적 구분)이 필요하면 둘을 합친 방식인 **세그먼테이션-페이징 혼용 방식**을 사용한다.
