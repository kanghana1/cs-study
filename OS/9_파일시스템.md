# 9. 파일 시스템

실제 디스크 자체는 번호가 매겨진 블록들의 집합이다. 쉽게 말하면 데이터를 담는 칸인 셈이다. 그런데 우리가 보는 디스크는 조금 다르다. 디스크에 여러 폴더들과 파일들이 들어있는 구조를 하고있는데, 이렇게 **사용자가 보는 디스크와 실제 디스크의 간극을 메워주는 게 파일시스템**이다.

<br>

## **파일 시스템**

**파일 시스템**은 디스크의 물리적인 블록들을 **사람이 이해하기 쉬운 파일과 디렉토리라는 단위로 추상화해서 관리**하는 OS의 한 부분이다.

예를 들어, 내가 보고서.pdf를 열면, 파일시스템은 해당 파일이 있는 디스크 블록을 가져다 주는 것이다.

<br>

### **파일 시스템이 하는 일**

**1. 추상화**

블록 번호같은 물리적 디테일을 숨기고, 익숙한 단위(파일, 폴더)로 제공한다.

**2. 공간 관리**

어떤 블록이 사용중이고, **어떤 블록이 비어있는지 추적**하고, 새 파일이 들어오면 **비어있는 블록을 찾아 할당**한다.

**3. 접근 제어와 메타데이터 관리**

파일의 크기, 생성 날짜, 소유자, 권한 같은 **정보(메타데이터)를 관리**하고, 누가 이 **파일에 접근할 수 있는지 통제**한다.

<br>

이러한 메타데이터는 빠른 탐색과 관리의 일관성을 위해 파일 내용이랑 분리되어 따로 저장된다.

그렇다면 파일은 디스크에 어떤식으로 배치될까?

<br>

## **파일 할당 방식 (File Allocation)**

파일을 디스크 블록에 어떻게 배차할 것인가에 따라 3가지 방법으로 나뉜다.

### **1. 연속 할당 (Contiguous Allocation)**

파일을 연속된 블록에 통째로 저장하는 방식이다. 연속으로 저장하기 때문에, 파일 정보로는 **시작 블록 번호와 길이만 저장**하면 된다.

```
디스크
┌────┬────┬────┬────┬────┬────┬────┬────┐
│    │ A  │ A  │ A  │    │ B  │ B  │    │
└────┴────┴────┴────┴────┴────┴────┴────┘
       └─파일 A─┘        └파일 B┘

파일 A: 시작 블록 1, 길이 3
파일 B: 시작 블록 5, 길이 2
```

**장점**

- 접근이 빠르고 단순하다.
  - 시작 위치만 알면 순서대로 읽으면 되기 때문에 순차접근이 빠름
  - 특정 위치로 바로 가는 직접 접근도 쉬움

**단점**

- **외부 단편화 문제**가 발생한다.

  - 지워지다보면 빈 블록이 여기저기 흩어져 공간은 충분한데 연속된 자리가 없어 넣지 못하는 현상이 생길 수 있음

- **파일 크기를 늘리기 어렵다.**
  - 연속된 자리에 공간이 이미 차있으면 통째로 다른 곳으로 옮겨야 함

<br>

### **2. 연결 할당 (Linked Allocation)**

연속 할당의 **외부 단편화 문제를 해결**하기 위해 나온 방식으로, **파일을 흩어진 블록에 저장하되 각 블록이 다음 블록을 가리키게 하는 방식**이다. (Linked List와 동일한 구조)

```
디스크 (블록마다 다음 블록 주소를 가짐)
┌────┐    ┌────┐    ┌────┐    ┌────┐
│ A  │───→│ A  │───→│ A  │───→│ A  │──→ null
│ #2 │    │ #7 │    │ #4 │    │ #9 │
└────┘    └────┘    └────┘    └────┘
 블록1     블록2      블록7     블록4

파일 A: 시작 블록 1 (나머지는 따라가면 됨)
```

파일 정보로는 **시작 블록 번호**만 저장하면 된다.

**장점**

- 외부 단편화 문제가 사라진다.
  - 연속된 공간이 필요없어짐
  - 파일 크기를 늘리기도 용이

**단점**

- 직접 접근이 불가하다.
  - 중간 블록을 찾을 수 없고, 첫 블록에서 따라가야함
  - 순차 접근만 효율적
- 포인터가 차지하는 공간이 있고, 안정성 문제가 크다.
  - 중간 블록의 포인터가 손상되면 체인이 끊김

<br>

### **3. 인덱스 할당 (Indexed Allocation)**

연결 할당의 **직접 접근 불가 문제를 해결**한 방식으로, 각 블록에 **포인터를 분산**시키는 대신 블록 주소들을 한 곳에 모아둔 인덱스 블록을 따로 둔다.

```
인덱스 블록 (파일 A 전용)        디스크 데이터 블록
┌──────────┐
│ 0 → #2   │ ───────────────→  블록2: A의 1번째
│ 1 → #7   │ ───────────────→  블록7: A의 2번째
│ 2 → #4   │ ───────────────→  블록4: A의 3번째
│ 3 → #9   │ ───────────────→  블록9: A의 4번째
└──────────┘
```

파일마다 인덱스 블록이 하나씩 있고, 거기에 데이터 블록들의 주소가 순서대로 적혀있다.

**장점**

- **직접 접근이 가능**해진다.

  - 인덱스 블록의 항목만 보면 바로 주소를 알 수 있음

- **외부 단편화 문제도 없어진다.**

**단점**

- **인덱스 블록 자체가 공간을 차지**한다.

  - 작은 파일이라도 인덱스 블록 하나는 무조건 있기 때문에 낭비될 수 있음

- 인덱스 블록 하나에 담을 수 있는 주소 개수가 정해져있다.
  - 큰 파일은 인덱스 블록 하나로 부족

<br>

그럼, 파일의 크기가 커서 한개의 인덱스 블록으로 되지 않는 경우는 어떻게 해야할까? 총 3가지 방법이 있다.

<br>
<hr>
<br>

**1. 연결 방식 (Linked Scheme)**

```
인덱스 블록1            인덱스 블록2
┌──────────┐          ┌──────────┐
│ → 데이터 │          │ → 데이터 │
│ → 데이터 │          │ → 데이터 │
│ → 데이터 │          │ → 데이터 │
│ → 블록2  │ ───────→ │ → null   │
└──────────┘          └──────────┘
```

- 인덱스 블록의 마지막 항목을 **다음 인덱스 블록**을 가리키게 함
- 연결 할당과 동일한 단점이 있음 (직접접근 불가)

**2. 다단계 인덱스 (Multilevel Index)**

```
1차 인덱스 블록        2차 인덱스 블록들       데이터 블록
┌──────────┐          ┌──────────┐
│ → 2차블록1│ ───────→ │ → 데이터 │ ─────→ 실제 데이터
│ → 2차블록2│          │ → 데이터 │
│ → 2차블록3│          └──────────┘
└──────────┘
```

- 인덱스 블록이 데이터를 직접 가리키지 않고, 또 다른 인덱스 블록을 가리키게 함
- 1차 인덱스가 100개를 가리키고, 각 2차 인덱스가 또 100개를 가리키면 100 × 100 = 10,000개 블록을 다룰 수 있음

**🌟 3. 결합 방식 (Combined Scheme) - inode**

실제 리눅스/유닉스가 쓰는 방식으로, 대부분의 파일은 크기가 작다는 것을 이용한 방식이다.

작은 파일은 빠르게, 큰 파일도 가능하게 만드는 게 목적이다.

```
inode 안의 포인터들
┌─────────────────────┐
│ 직접 포인터 ×12      │ → 데이터 블록 직접 가리킴 (작은 파일용)
├─────────────────────┤
│ 단일 간접 포인터 ×1  │ → 인덱스 블록 → 데이터
├─────────────────────┤
│ 이중 간접 포인터 ×1  │ → 인덱스 → 인덱스 → 데이터
├─────────────────────┤
│ 삼중 간접 포인터 ×1  │ → 인덱스 → 인덱스 → 인덱스 → 데이터
└─────────────────────┘
```

작은 파일은 직접 포인터만으로 바로 접근하고(빠름), 파일이 커질수록 간접 포인터를 단계적으로 동원하는 방식이다.

가장 중요하기 때문에, 따로 정리해두려고 한다.

<br>

## **inode (인덱스 노드)**

**inode**는 **하나의 파일에 대한 모든 메타데이터와 데이터 블록 위치를 담는 구조체**이다.

위에서 정리했듯이, 파일은 메타데이터를 별도의 공간에 저장해두고, 그 장소가 inode인 것이다. **파일 하나당 inode 하나**가 있다.

<br>

### **inode 구조**

inode는 크게 두 부분으로 나뉜다.

**위쪽**은 파일에 대한 정보인 **메타데이터**가 들어있고, **아래쪽**은 **실제 데이터가 어디있는지 가리키는 포인터**들이 들어있다.

```
inode 구조
┌──────────────────────────┐
│  [메타데이터]             │
│  - 파일 타입 (파일/디렉터리)│
│  - 권한 (읽기/쓰기/실행)   │
│  - 소유자 (UID, GID)      │
│  - 파일 크기              │
│  - 타임스탬프 (생성/수정) │
│  - 링크 수                │
├──────────────────────────┤
│  [데이터 블록 포인터]     │
│  - 직접 포인터 ×12        │
│  - 단일 간접 포인터 ×1    │
│  - 이중 간접 포인터 ×1    │
│  - 삼중 간접 포인터 ×1    │
└──────────────────────────┘
```

**데이터 블록 포인터**

inode의 아래쪽에는 데이터 블록 포인터들이 들어있다. 포인터들은 역할에 따라 종류가 나뉜다.

- **직접 포인터 (Direct)**

  - 데이터 블록을 직접 가리킨다.
  - 포인터 한 개는 하나의 데이터 블록을 가리킨다.
  - 작은 파일은 이걸 사용해 빠르게 접근할 수 있다.

- **단일 간접 포인터 (Single Indirect)**

  - 인덱스 블록 하나를 가리킨다.
  - 인덱스 블록 안에는 여러 데이터 블록 주소가 있다.

- **이중 간접 포인터 (Double Indirect)**

  - 인덱스 블록이 인덱스 블록을 가리킨다.
  - **인덱스 블록 → 또 인덱스 블록 → 데이터**

- **삼중 간접 포인터 (Triple Indirect)**
  - **인덱스 → 인덱스 → 인덱스 → 데이터**

```
inode
├── 직접 ×12        ──────────────→ 데이터 (작은 파일, 빠름)
├── 단일 간접 ──→ [인덱스] ────────→ 데이터
├── 이중 간접 ──→ [인덱스] → [인덱스] → 데이터
└── 삼중 간접 ──→ [인덱스] → [인덱스] → [인덱스] → 데이터
                                        (큰 파일까지 감당)
```

위 구조를 이용하여 대부분을 차지하는 **작은 파일**은 **직접 포인터만으로 즉시 접근**이 가능하게 하고, 공간 낭비도 없다.

**큰 파일**이 와도 **간접 포인터를 이용해 수 GB까지 감당**할 수 있게 된다!

<br>

## **디렉토리 (Directory)**

디렉토리는 파일을 넣어두는 폴더로 사용한다!

<br>

### **디렉토리와 inode**

inode는 별도의 이름을 갖지 않고, 디렉토리와 연결되어있다.

즉, 디렉토리는 파일 이름과 inode 번호를 매핑하고 있다.

```
디렉터리 (예: /home/하나)
┌─────────────┬────────────┐
│  파일 이름  │ inode 번호 │
├─────────────┼────────────┤
│ 보고서.docx │    2851    │
│ 여행.jpg    │    3902    │
│ 메모.txt    │    4127    │
└─────────────┴────────────┘
```

위 표의 각 줄(이름 + inode 번호)을 **디렉토리 엔트리**라고 한다.

<br>

> **🔗 파일을 여는 과정**
>
> 1. 디렉터리에서 "보고서.docx" 라는 이름을 찾음
> 1. 그 이름에 연결된 inode 번호(2851)를 얻음
> 1. 2851번 inode를 읽음 → 메타데이터 + 데이터 블록 위치 파악
> 1. 데이터 블록에서 실제 내용을 읽어옴

<br>

### **왜 inode에서 이름을 분리했을까?**

inode와 이름을 분리함으로써 **하나의 파일에 여러 이름**을 붙일 수 있게 된 것이다! 이게 우리가 알고 있는 **하드링크(Hard Link)** 이다.

메타데이터에 **링크 수**라는 게 있는데, 이게 해당 inode를 가리키는 이름의 개수이다. 링크 수가 0이 되면 파일을 진짜로 삭제한다.
